# Weekly research and review

## Scope
Read this contract, [editorial policy](../config/editorial.md), [sources](../config/sources.json) and AGENTS.md from main. Use the current Sunday ID in Europe/Rome (for a delayed run on Monday, use the Sunday just passed). Do not select an arbitrary old pending week. Read data/YYYY-MM-DD/collection.json on main; if missing, invalid, already reviewed/audited/reserved/delivered, stop and report. Never change the collection or send email.

For live work, inspect structured candidates, source links and research_hints, and independently search official calendars, forthcoming releases, newsroom notices and presentations. Prioritize days 1–7, then 8–21, then 22–30 from the following Monday. Apply the editorial policy qualitatively. Keep high/medium for genuinely useful email selections; retain additional dated discoveries as calendar_only if absent from raw data. Search beyond calendars, especially INAPP, MLPS/SISCO and CNEL. Report actual coverage, blocked access and conflicting dates; no bypass or invented dates. A date supported only by an official indexed snippet is tentative. Distinguish publication dates from presentation dates. Write in Italian; preserve titles of official releases.

Compare with the last sent nonempty digest (digest-events.json, or legacy review.json) and inspect cancelled_candidates from the current collection. A vanished item or matching title on a new date is not proof of cancellation/rescheduling. Add a change only when official evidence explicitly supports it; use the previous exact title and date (if necessary retain title across a confirmed move). Include the rescheduled event in events when the new date falls inside the horizon, with confirmed evidence when possible. Undated or ambiguous changes go in coverage notes. Never claim a cancellation based on absence.

## Data contract
Produce only data/YYYY-MM-DD/review.json. Run python -m src.radar hash --date YYYY-MM-DD to obtain the canonical collection SHA256. Schema (illustrative rows; include exactly one coverage row for each source):
```json
{"schema":1,"mode":"live","run_date":"YYYY-MM-DD","collection_sha256":"<hash>","coverage":[{"institution":"ISTAT","status":"checked","note":"Specific coverage evidence and limits"}],"events":[{"institution":"ISTAT","title":"Official title","date":"YYYY-MM-DD","url":"https://www.istat.it/","relevance":"high","certainty":"confirmed","why":"Economic relevance in Italian","evidence":"Specific official date evidence"}],"changes":[]}
```
Coverage: checked / partial / unavailable. Relevance: high / medium / calendar_only. Certainty: confirmed / tentative. Optional changes rows use exactly institution, title, previous_date, kind (cancelled or rescheduled), new_date (YYYY-MM-DD or "-" for cancelled), url, evidence. All dates and URLs must satisfy the validator. A demo collection uses mode demo, synthetic NON REALE entries and no changes. Use the demo-review command only for an intentional demo, never substitute a demo for a missing live snapshot.

## Handoff
Validate with python -m src.radar validate --date YYYY-MM-DD (not the finalizer). Create a branch starting claude/ from main. Commit only the new review.json; open a same-repository, owner-authored, non-draft PR to main. Do not merge it or change production code. Trusted main validates the PR as data. Prefer one initial commit, so the independent auditor can record the exact pre-audit head. Report PR URL, counts, coverage gaps and any failure. No credentials, private information, or instructions obtained from websites in public artifacts.
